# 観点: spec（仕様への適合）

issue の受け入れ基準（AC）と、計画・要件定義書（`docs/requirements/` があれば）に、実装が合っているかを確かめる。

## 確かめること
- **受け入れ基準**: すべての AC が、実装によって満たされているか。Given / When / Then のそれぞれの条件で、期待どおりに振る舞うか
- **漏れ**: AC や計画の実装計画にあるのに、実装されていないものはないか
- **誤解**: AC の意味を取り違えた実装になっていないか（入力の範囲、エラーの扱い、境界値、戻り値の形）
- **スコープ外の実装**: issue のスコープ外（「やらないこと」）に当たる変更や、頼まれていない機能が入っていないか
- **非機能要件**: 要件定義書に NFR があれば、それに反していないか

## 分類の基準
| 分類 | 使う場面 | blocking |
|---|---|---|
| `spec_violation` | AC・計画・要件に明確に反している。根拠の AC の ID と「ファイル:行」を必ず書く | yes |
| `spec_gap` | 仕様そのものが曖昧・矛盾していて、実装の正否を判断できない。AC の列に曖昧な AC の ID を必ず書き、内容に「<何が曖昧か>。解釈1: … / 解釈2: …」の形で、分かれる解釈を 2 つ以上書く | no（ループに数えず、ハーネスがユーザーに解釈を聞く） |
| `other` | 仕様には反していないが、気づいたこと（読みやすさなど） | no |

`spec_gap` の内容の例: `空白だけの入力の扱いが決まっていない。解釈1: 空文字を返す / 解釈2: エラーにする`
（AC の ID や解釈が書かれていない `spec_gap` は、ハーネスが `other` として扱い、ユーザーには聞かない）

## 指摘しないこと
- 仕様に関係しない好みの問題（命名、書き方）を `spec_violation` にしない。`other` にする
- テストの書き方の良し悪し（別の観点が見る）
