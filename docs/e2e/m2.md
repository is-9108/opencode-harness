## 1. シナリオ

各シナリオで記録すること: エスカレーションの有無と理由、ループの回数（`state.json` の `testFix` / `reviewFix` / `autoFixUsed`）、子セッションの数（`harness_status`）、トークン数（PR 本文の「ハーネスの記録」）、所要時間。

### A. 直せない失敗（AC-1）

- **用意するもの**: 既存のテストと、新しい issue の受け入れ基準が食い違う状態を作る。
  - 例: 既存のテストが `formatPrice(1000) === "1,000円"` を確かめている。issue の AC は「`formatPrice(1000)` は `¥1,000` を返す」
  - 既存のテストはベースラインでは通るので除外されない。テストはロックされるので、実装だけではどちらかが必ず失敗する
- **期待する動き**:
  1. checks が失敗し、test-fix に入る
  2. 直した後も同じ失敗の指紋が 2 回続き、`no_progress` でエスカレーションする
  3. `/fix <issue>` で、報告の要約と方針の選択肢（直す / テストの変更を申請する / 今は止める）が示される
  4. 「テストの変更を申請する」を選び、harness-fix が既存のテストの変更申請を書く → `fix-1.md` → `harness_advance` → 申請の承認を求められる → 承認 → test-writer がテストを変える → checks → review（human モード）→ PR
- **注意**: test-fixer が食い違いに気づき、`no_progress` の前にテストの変更申請を書くことがある（`test_change_request` でエスカレーション）。そうなった場合も記録する。AC-1 の `no_progress` を確かめたいなら、issue の AC を既存のテストと食い違うと気づきにくい書き方にする

### B. 仕様の曖昧さ（AC-2）

- **用意するもの**: 受け入れ基準に抜けがある issue。
  - 例: 「空文字を渡したら空文字を返す」とだけ書き、空白だけの入力の扱いを書かない
- **期待する動き**: review で `spec_gap` が出て、ループの回数（`reviewFix`、`autoFixUsed`）を増やさずに `need_user` で解釈の選択肢が示される。回答すると `04-decisions.md` に記録され、決まった解釈でもう一度レビューして PR まで進む。`issue-comment-draft.md` ができ、issue へのコメントは投稿されない
- **注意**: レビュアーが曖昧さに気づかない、または「解釈1: … / 解釈2: …」の形で書かないことがある。その場合は `other` として扱われ、聞かずに進む。何回試して何回聞かれたかを記録する

### C. 不安定なテスト（AC-3）

- **用意するもの**: 実行ごとに結果が入れ替わるテストを、issue と関係のない既存のテストとして置く。
  - 例: テストの中で `os.tmpdir()` の回数ファイルを読み書きし、偶数回目だけ失敗する
  - `harness.config.json` の `tests.flakyRetries` は 1 以上
- **期待する動き**: checks で失敗しても、再実行で通れば flaky として `checks/run-<n>.md` と PR 本文に載り、test-fix に入らずに PR まで進む
- **注意**:
  - 子セッションもテストを実行するので、checks の 1 回目が偶数回目になるとは限らない。1 回目で通ったら flaky は記録されない。PR 本文に flaky が載るまで、別の issue で繰り返す
  - ベースラインの実行で失敗すると、flaky ではなくベースラインの失敗として除外される

## 3. 実行の手順

TUI で `/dev <issue>`、エスカレーションしたら `/fix <issue>` を実行し、問いに答える。

M1 と同じく、`opencode serve` と [spikes/m1/drive-dev.mjs](../../spikes/m1/drive-dev.mjs) で操作を自動にしてもよい。ただし、このスクリプトは計画の承認と依存先の確認にしか答えられない。spec_gap の問いと `/fix` の方針の問いには、手で答えるか、スクリプトを拡張する。
