### 起動の方法

```bash
# 1.18.31 専用のデータの置き場所で起動する（v2 のデータとは分ける）
alias oc118='XDG_DATA_HOME=$HOME/oc118/data XDG_STATE_HOME=$HOME/oc118/state XDG_CACHE_HOME=$HOME/oc118/cache $HOME/.local/bin/opencode'
oc118 auth login     # データの置き場所を分けたので、ログインし直す
```

- SSH 越しの ChatGPT のログインは、ブラウザからの戻り先（Raspberry Pi の `localhost:1455`）に届かず失敗することがあった。`ssh -L 1455:127.0.0.1:1455` でポートを転送し、ログインの待ち受け中に何も押さずにブラウザで認証すると成功した

## シナリオの作り方（やり直すときのために）

- **不安定なテスト**: ハーネスの run の状態（`.harness/runs/*/state.json`）を読み、この worktree の run が checks の工程にいるときだけ、1 回目に失敗して再実行で通るテストを置いた。最初は環境変数とベースラインのファイルの有無で判定したが、red の確認や子セッションもテストのコマンドを実行するため、checks の 1 回目で失敗しなかった
- **直せない失敗**: worktree の外（`~/e2e-unfixable.mjs`）に、ベースラインの記録の後だけ同じエラーで失敗するスクリプトを置き、`harness.config.json` の checks に足した。子セッションからは読めず、書き換えもできないので、確実に `no_progress` になる。`/fix` では、設定からこのチェックを外してコードを変えずに再開した
- 既存のテストとの食い違い（#10）と、矛盾した受け入れ基準（#16）では、直せない失敗にならなかった（下の問題 4、5）

## 見つかった問題と対応

| # | 問題 | 対応 |
|---|---|---|
| 1 | Raspberry Pi に入っていた opencode v2.0.14 では、ハーネスのプラグインが読み込まれない（`.opencode/package.json` と `node_modules` が作られず、ツールが見つからない） | 1.18.31 を別に入れて使った。v2 への対応は未定（プラグインの仕組みの変更を調べる必要がある） |
| 2 | 最初に用意した不安定なテストが、checks の 1 回目で失敗しなかった（シナリオの不備） | run の状態を読んで checks の工程でだけ働くように直した |
| 3 | 不安定なテストが Node の API を使うため、試験用リポジトリの typecheck でエラーになった（ベースラインの失敗として除外された） | テストに `// @ts-nocheck` を付けた（シナリオの不備） |
| 4 | **red の工程で、test-writer が既存のテストを承認なしに消して書き換えた**（#10 の `[既存] 3 桁区切りで円を付ける`）。テストのロックは red の後なので、red の間は守られていない。今回は受け入れ基準どおりの正しい変更だったが、仕様と関係なく既存のテストを消したり弱めたりすることもできる | 未対応。red の確認で既存のテストの削除・変更を検出して PR 本文に載せるか、承認を求める。M3 の test-integrity の観点でも見る |
| 5 | **矛盾した 2 つのテストを通すため、implementer が呼び出すたびに結果を交互に変える実装を書いた**（テストの捻じ曲げ）。spec のレビュアーはこれを `test_gaming` ではなく `spec_gap` として挙げ、選択肢に「交互に返す」が入り、それを選ぶと PR まで通った（#16） | 未対応。M3 の test-integrity の観点で `test_gaming` を blocking にする。spec のレビュアーには、状態を持って結果を変えるような実装を spec_gap にしないよう指示する |
| 6 | spec_gap の選択肢の最後に、レビュアーの補足（「現在の実装は解釈2。」）が混ざった（#11） | 未対応。選択肢の読み取りか、レビュアーへの書き方の指示を直す |
| 7 | 子セッションに許すコマンドが広すぎる。checks のコマンドの先頭 2 語で許可するため、`npx tsc` なら `npx` で始まるコマンドをすべて、`FLAKY_ARM=1 npx vitest` なら `FLAKY_ARM=1 npx` で始まるコマンドをすべて実行できる | 未対応（実害は出ていない）。checks のコマンドそのものか、決まった形だけを許可する |
| 8 | `/fix` で、harness-fix が修正の記録（`fix-1.md`）を書かずに止まった。方針の選択の後、コードを変えない修正（設定を直しただけ）で記録を書く流れが伝わらなかったようで、記録は手で書いた | 未対応。harness-fix の指示文に、コードを変えない場合も記録を書いて `harness_advance` を呼ぶことを明記する |
| 9 | E2E のためのコマンドでつまずいた（`/dev C` のように issue の番号を置き換えなかった、`$12` がシェルで `$1` と `2` に分かれた） | 手順の書き方の問題。次の E2E の手順では、番号を変数に入れる形に統一する |
