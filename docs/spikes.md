# M0 スパイク結果

- 実施日: 2026-09-26
- 環境: opencode 1.18.31 / Windows 11 / Node 22.17
- 方法: sandbox のリポジトリで `opencode serve` を起動し、HTTP API（SDK と同じ API）と検証用プラグインで確かめた
- 再現用のスクリプト: [spikes/m0/](../spikes/m0/)（`t<番号>-*.mjs`）。検証用のエージェントとプラグインは、スクリプトの冒頭のコメントを参照

## 結果の一覧

| # | 確かめたこと | 結果 | 根拠 |
|---|---|---|---|
| 1 | `session.prompt` の body で `agent` を指定できるか | ✅ できる | 指定したエージェントのシステムプロンプトどおりに応答した（`AGENT-OK`）。応答の `info.agent` にも反映される |
| 2 | プラグインのツールを 30 分以上実行できるか / Esc での中断が伝わるか | ✅ どちらもできる | 1900 秒（31 分 40 秒）のツール実行が最後まで完了し、エージェントも応答を返した。`session.abort` から約 13 秒で、ツールの `context.abort` に中断が伝わった。注意: ① ツールが正常に終わった直後にも `abort` のシグナルが発火する（後片付けによるもの。完了後のシグナルはユーザーの中断として扱わない）② 応答まで HTTP の接続を開いて待つと、クライアント側（Node の fetch）が 5 分で切れる。サーバ側の処理は続く |

| 5 | 同じ子セッションで、途中からモデルを替えて続けられるか | ✅ できる | `openai/gpt-6-luna` → `openai/gpt-5.5` に替えても、前の会話の内容（合言葉）を覚えていた |

## 重要な発見

### 1. 上限に達しても、エラーにならずに「待ち続ける」（#3）
- opencode は、OpenCode Go の上限エラー（`GoUsageLimitError`）を**リトライ可能**なエラーとして扱う。レスポンスの `retry-after` の時間だけ待ってから再試行する（最大 5 回）。
- 実際に起きたときの `session.status` のイベント:
  ```json
  { "type": "retry", "attempt": 1,
    "message": "monthly usage limit reached. It will reset in 17 days 10 hours. ...",
    "action": { "reason": "account_rate_limit", "provider": "opencode-go", "title": "Go limit reached", ... },
    "next": 1791856204932 }
  ```
- つまり、**何もしなければ、子セッションは 17 日間止まったままになる**。エラーを待つ方式では検知できない。
- **ハーネスでの対処**: `session.status` のイベントを購読する。`type: "retry"` のときに、次のどちらかに当てはまれば「上限到達」と判定する。そのセッションを `session.abort` で止め（`idle` に戻ることを確認済み）、fallback のモデルで同じセッションに続きを送る。
  - `action.reason` が `account_rate_limit` または `free_tier_limit`
  - 次の再試行までの待ち時間（`next - 今`）が、しきい値（例: 2 分）より長い
- `limitedUntil` には `next` の値をそのまま使える（リセット時刻が分かる）。
- Codex の上限も、429 と `retry-after` で返れば同じ経路になるはず（未確認。上の 2 つ目の条件で拾う）。

### 2. OpenCode Go は、現在「月間上限に到達済み」
- 検証中に、**このアカウントの OpenCode Go が月間上限に達している**ことが分かった（リセットまで約 17 日 10 時間、2026-10-13 ごろ）。無料モデル（`space-bunny-free`）も同じエラーになった。
- 当面は Codex だけで動かすことになる。上限状態の管理（`provider-status.json`）を早めに実装する価値が高い。

### 3. Codex（ChatGPT サブスク）では、使えないモデルがある
- `opencode models` に表示されても、ChatGPT アカウントでは 400 エラーになるモデルがある（エラーは即時に返る。リトライはされない）。

| 使える | 使えない |
|---|---|
| `gpt-5.5` `gpt-5.5-fast` `gpt-5.6-sol` `gpt-5.6-terra` `gpt-6-sol` `gpt-6-luna` `gpt-6-luna-fast` `gpt-6-astra` | `gpt-5.4` `gpt-5.4-mini` `gpt-5.3-codex-spark` |

- 計画の設定例で使っていた `openai/gpt-5.4-mini` は使えない。
- **ハーネスでの対処**: 設定の検証で、各モデルに短いプロンプトを送って疎通を確かめる（結果はキャッシュする）。

### 4. セッションごとに権限ルールを渡せる（#7 の副産物）
- `POST /session` の body に `permission: [{ permission, pattern, action }]` を渡せる。
- **計画への影響**: テストファイルの編集禁止や worktree への `external_directory` の許可を、エージェントの定義ファイルを生成して書き換えるのではなく、**子セッションを作るときに動的に渡せる**。sync で行う予定だった権限の生成が簡単になる。
- 注意: `external_directory` の確認に出たパスの一部が、実際のパスと異なっていた（原因は不明）。許可のパターンは、完全なパスではなく `*<worktreeのディレクトリ名>*` のようなワイルドカードにしておくのが安全。

### 5. その他、使えそうな API
| API | 用途 |
|---|---|
| `POST /session/{id}/prompt_async` | 完了を待たずに送る。ツールの長時間実行が問題になったときの代わりの方法 |
| `POST /tui/select-session` | TUI の表示を、指定したセッションに切り替える（子セッションの様子を見せる） |
| ツールの `context.metadata` / `context.ask` | ツールの実行中に進み具合を TUI に表示する / ツールから権限の確認を出す |
| `GET /session/{id}/children` | 子セッションの一覧（再開のときの照合） |

## 計画への反映が必要な点

| 計画の箇所 | 変更内容 |
|---|---|
| 6.1 フォールバック | 検知の方法を「エラーのパターンに一致」から「`session.status` が `retry`、かつ `action.reason` か待ち時間で判定 → abort → 切り替え」に変える。`limitedUntil` は `next` を使う |
| 6.2 対話する工程 | 司令塔のセッションでも同じ検知ができ、プラグインが abort して、fallback のモデルと agent を指定して続きを送れる（#5 と #9 の組み合わせ）。「プラグインからはモデルを変えられない」という v3 の前提は誤りだったので、**対話中でも自動で切り替えられる**ように直す |
| 6 設定の検証 | モデルの疎通の確認を追加する。設定例の `openai/gpt-5.4-mini` を、使えるモデル（例: `openai/gpt-6-luna-fast`）に替える |
| 8.2 / 9 権限 | テストのロックと worktree の許可は、子セッションの作成時に `permission` で渡す。sync でのエージェント定義の生成は、共通の deny（git の書き込みなど）だけにする |
| 8.4 レビュー | 「プロンプトの並び順でキャッシュを効かせる」は効果がないので削除する。レビューのトークンは「観点の数 × diff」で見積もる。advisory にまとめることの節約効果が相対的に大きくなる |
| 4 自動継続 | 自動で送るプロンプトには、agent とモデルを必ず指定する |
| 10 コスト | Codex はコストが 0 になることを確認した。予算はトークン数で管理する |
